# AirBorder implementation and evaluation plan

AirBorder helps connecting passengers understand their onward gate and decide which selected airport stops still fit. The programmed browser prototype supports a bounded, replayable planning demonstration. It does not yet establish reliable indoor positioning, personal walking-history integration, live occupancy or complete native interaction correctness. [The acceptance contract](Acceptance-and-review.md) records implemented foundations and pending central features separately.

## Implementation sequence and replication

Keep one revisioned journey shared by Flight, My plan, Map, Camera and notifications. Ordered stops use stable IDs and active/completed/removed state. Observations carry entity/source, event time, receipt time, expiry and live/synthetic origin. A disruption updates matching facts without replacing selections. Recalculate walking, queue, visit, transfer and security components once each. Unknown inputs cannot produce a definitive fit; departure delays do not extend airline deadlines. Distinguish an internal arrival target from a confirmed airline cutoff.

The canonical provider implementation is `Backend/src/index.js`; the browser adapter is `Web/backend/index.mjs`. Keep provider credentials, authentication and optional inference on the server. Do not fork provider-policy logic into the UI. Current local browser serving is a development/test facility, not a production security configuration. Review server bindings, feature flags, source rights and deployed provider access before any live-service claim.

Implement and verify in this order:

1. Preserve the approved Figma identity, original semantic colours and restored Haneda assets. Use the node/code mapping as a design reference; do not describe this as an installed Figma Code Connect integration.
2. Stabilize ordered state, replayable controlled-clock fixtures and deterministic route/recommendation rules. Require selected-versus-absent, used-versus-unused transfer, stale/unknown data, duplicate/out-of-order events, stale Apply and deadline cases before adding live feeds.
3. Complete B1/B2 critical navigation, prominent gate update and route progress behaviour; then additive planning, lounges, Map/Camera continuity and alternatives. Complete typed input, camera/location denial and recovery rather than testing only happy paths.
4. Implement automatic walking-source selection, consent/revocation and Previous Trips. Specify quality/outlier and retention rules before collecting history; separate airport walking from waiting and everyday health activity. Average estimates remain available without health access.
5. Add one source adapter at a time: flight identity/date/gate/deadline first; airport-coordinate/time-window weather next; operator/café/accessibility only when an authorized real source exists. Weather supports relevant selected-outdoor-stop advice, not invented closures or flight cancellations. Retain offline/unknown paths and isolated synthetic sessions.
6. Add optional LLM explanation only after deterministic calculation passes. Supply approved fact/candidate IDs, keep numerical values/actions under program control, validate returned references, and use templates after timeout/refusal/invalid output. The model cannot create stops, calculate authoritative deadlines, apply changes or receive ticket images/passports/raw health data.

From a clean checkout, install Backend dependencies before starting the browser server or its HTTP tests (`npm ci --prefix Backend`). Run these checks from the indicated directories. Save results against the exact reviewed revision. Browser API fixtures and intercepted responses are controlled tests, not evidence that a provider is deployed.

| Directory | Check | Purpose |
| --- | --- | --- |
| `Web` | `npm ci --ignore-scripts`; `npm run test:engine` | Deterministic selection, timing, event and revision invariants. |
| `Web` | `npx playwright install chromium`; `npm test` | Real Chromium interaction with local test server; selected mobile widths, guide/plan behaviour and selected presentation checks. |
| repository root | `node --test Web/backend/test/*.test.mjs` | Browser API contract, origin/auth/validation/rate-limit behaviour and local HTTP integration. |

Do not use a completion percentage without a denominator. Freeze the central requirements before calculating it: report accepted requirement groups divided by total central groups, with partial groups listed separately and no automatic half credit. A weighted measure requires weights chosen before scoring. Current documentation does not assert a project-wide percentage because central features remain pending and test execution is being refreshed.

## Planned evaluation

This is an evaluation plan; no participants have been recruited and no user-study results are claimed. Software tests and questionnaire examples are not participant evaluations. The course assignment requires a programmed interactive prototype, a 5–10-page ACM double-column report excluding appendix, and a 4–5-minute video. The report must contain Introduction, Initial Design, System, Implementation Status and Evaluation Plan. The required course sections override the usual preference for fewer headings. The video needs a title with group/member names, brief users/problem and evaluation screens, and mostly working-system demonstration. Populate required names from the actual team record; do not invent them.

Recruit adults who have made an airport connection or expect to travel, including participants with varied airport familiarity and mobile confidence. Invite through permitted course/community channels without instructor pressure, record eligibility and prior experience, and seek mobility-related perspectives without treating a small convenience sample as representative. Confirm course level and group size before recruitment: graduate groups require at least three evaluations per member; undergraduate groups require at least two. These are assignment minima, not a power calculation. Obtain appropriate course/institution approval and informed consent before data collection; avoid collecting ticket, health or passport data.

Use a within-subjects comparison of the revised implementation and a frozen baseline with equivalent functionality for the measured tasks. A static Figma frame cannot be treated as equivalent to a programmed baseline for interaction time. If no comparable executable baseline exists, implement the comparison task subset first or explicitly change to a single-system descriptive usability study and revise the comparative hypotheses before recruitment. Do not compare incompatible systems and attribute every difference to the design change.

Primary hypothesis H1: the revised interface increases the proportion of independently completed planning-and-recovery tasks relative to baseline. Null H01: completion proportion is equal. Primary hypothesis H2: the revised interface reduces time to correctly identify the current gate and retain a feasible selected plan after disruption. Null H02: correct-completion time is equal. Secondary hypotheses: the revision reduces navigation errors/assistance and improves post-task ease ratings; corresponding nulls specify equal error counts, assistance rates and ratings. Preference and interview findings explain possible causes rather than proving operational travel safety.

Use the same phone-sized Chromium device configuration for both conditions, the same input method, controlled start state and comparable synthetic fixture values. Run seated in a quiet room or a controlled remote session; record which setting was used. Have a facilitator and event timer/log, plus optional consented screen recording. Do not run physical airport navigation tasks from unverified topology. Reserve approximately 35–45 minutes per participant: consent/eligibility 5 minutes, neutral orientation/practice 5, two conditions about 10–12 each, then questions/debrief 5–10. Pilot the duration and task wording without including pilots in the final analysis unless declared in advance.

Randomly assign balanced AB/BA condition orders, and swap matched fixture versions to reduce memorization. Reset each condition to its specified manifest and clock. Give the same neutral instructions and no coaching; log any assistance. The facilitator reads these tasks in order within each condition:

1. Find your onward flight and current gate. Add a café and lounge; show which stops are saved and remove the lounge. Success: correct flight/gate, café retained, lounge removed, and participant can identify the remaining route.
2. Begin guidance, advance one step and switch Map/Camera or the equivalent supported route views. Return to the same destination/step. Success: participant reaches the current-step display without restarting the journey.
3. Release the matched gate/queue disruption. Ask the participant to identify the new gate and decide what to do with their selected plan. Success: correct complete gate identifier, no unselected-stop decision, and an explicitly accepted valid change or justified retention based on the displayed facts.
4. Present unknown queue information or denied location/camera permission. Ask how to continue. Success: participant recognizes the uncertainty and reaches the supported fallback without treating unknown as zero or losing the plan.

Start a task timer when the facilitator finishes reading; stop at the predefined correct state or a three-minute cap. Record success without help, success with help, incorrect completion, or timeout/abandonment separately. Do not code assisted completion as independent success. Use equivalent tasks only when both frozen conditions support them; newly added features can receive separate descriptive tests without entering the paired primary comparison. Log fixture/version, condition order, task, elapsed time, actions, wrong turns, assistance and outcome using anonymous participant IDs. Avoid collecting personal travel details.

Primary metric one is each participant's fraction of eligible tasks completed independently; primary metric two is elapsed time for the gate/disruption task with correctness reported alongside it. Report failures and censored three-minute tasks separately; do not silently drop failures from time comparisons. Secondary metrics are wrong-screen/backtracking count, facilitator-help count, gate-identification error count, and a consistent seven-point post-task ease item: “How easy or difficult was this task?” from very difficult to very easy. Ask after each condition: “Which information helped you decide?”, “What was unclear about the route or saved stops?”, “What did you think unknown information meant?” and “What would you need before relying on this during a connection?” Finally ask preference and why.

For the graduate quantitative analysis, treat the participant as the analysis unit; repeated tasks are not independent extra participants. Predeclare the paired comparison, primary endpoints and missing-data handling. Report paired differences with confidence intervals and individual outcomes; for a small sample use a paired permutation/sign-based method as appropriate to the endpoint, documenting assumptions. If testing both primary hypotheses, predeclare multiplicity handling such as Holm adjustment. Present secondary measures as exploratory and discuss condition-order effects, convenience sampling, learning, small sample uncertainty and synthetic airport conditions. Do not interpret a non-significant result as equivalence or infer actual missed-flight risk from this usability study.

Freeze protocol and success rubrics before recruitment, pilot instrumentation, retain consent separately from anonymized logs, and define access/retention/deletion before recording. The final report must distinguish planned from completed evaluations and report deviations. Raw peer CSVs, private source PDFs and personal paths do not belong in published repository artifacts.
