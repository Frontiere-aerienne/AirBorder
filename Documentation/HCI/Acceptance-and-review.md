# AirBorder acceptance and review contract

The programmed prototype must preserve the traveller's selected plan while changing its guidance in response to relevant facts. The authoritative visual reference is the [AirBorder Prototype page](https://www.figma.com/design/zQaZKxZ1rrX4EMYQkY3j00/AirBorder-Travel-Companion?node-id=858-8324). This contract translates the reviewed implementation plan into release checks. It does not certify the current branch, physical navigation or live-provider operation.

The peer-review record contains 14 substantive responses and eight blank records. All substantive suggestions remain in scope; repeated suggestions share requirements without losing their response numbers. Positive feedback constrains preservation of the original colours, introductory guidance, facility cards, backgrounds and airside/landside grouping. Engineering additions such as the synthetic driver, provider adapters and bounded LLM are implementation choices, not quotations from peers.

## Status and evidence rules

Use four distinct statuses: **implemented** means code exists for the stated bounded behaviour; **machine checked** requires a passing named test against the reviewed revision; **interaction/visual checked** requires recorded observed behaviour or screenshots; **pending** means an acceptance condition still lacks evidence. A test file alone does not establish a pass. A Figma interaction is not a live application integration. A passing browser suite is not a native-suite result or a usability study.

The October 11 historical native record reports 106 passing unit tests and 10 failures among 17 UI tests. It remains an unresolved historical failure until a fresh native run establishes the disposition of those cases; see [the verification snapshot](../Verification-2026-10-11.md). Do not replace it with browser results. Do not claim that all requirements are implemented, that the system is bug free, or that synthetic estimates establish real-world accuracy.

Local validation for this implementation passed 33 Chromium tests, 16 journey-engine tests, 12 browser API/HTTP tests and 37 canonical Worker tests (98 application tests total, no skips; four additional CI simulator-selection tests also pass). Browser tests include real local HTTP directory/timing, delayed-response invalidation, unknown/stale inputs, directory outage, axe checks on four views in the phone shell, keyboard focus/skip navigation, selected mobile targets, source information in Help/About without a persistent banner (explicit user request), direct-to-gate plan retention, guide progress preservation through desktop/mobile direct entry, and expired-gate confirmation with no saved stops, explicit visit completion without revisiting or deleting the remaining plan, active-route reconciliation after adding a stop, and iPhone 13/wide-window phone composition. Hosted results must still be checked against the exact PR head; these counts do not certify the native suite. Screenshots are review attachments, without a static visual regression baseline; automated accessibility checks do not establish full accessibility or assistive-technology support.

## Review gates for every change

1. Map the changed behaviour to the IDs above and its source. Inspect the shared state, provider boundary, dynamic copy and all entry points affected. The reviewer must read this contract and the implementation/evaluation plan, not only the patch.
2. Run required regression checks for the changed layers: engine, browser integration, browser API/HTTP wrapper and canonical Worker. The native build/unit/UI job also runs on every PR, including browser-only changes. Save revision, command, environment, pass/fail/skip counts and artifact references; an unavailable job is pending, never passed.
3. Obtain an automatic Codex review of the current patch against these requirements. Require findings with severity, file/line, trigger and violated criterion; resolve actionable findings and review fixes. A required review job or required test failure must block merge. Automated review supplements execution and human judgment; it is not proof of complete correctness. The repository settings were verified to require `Build and test` and `HCI required tests` from GitHub Actions, an up-to-date branch, one fresh independent approval and resolved conversations, including for administrators. Codex review is configured for all PRs on every push; extra-credit spending remains off. Codex does not provide the required human approval.
4. Verify affected complete journeys, same-scenario Map/Camera/tab transitions and denial/recovery branches. Compare screenshots to the Figma reference, preserving approved colours and Haneda assets. Apply **USER-COPY-01** to defaults and runtime strings in every supported locale.
5. Update the status ledger only from observed evidence. Record residual limitations. Post anchored Figma implementation comments only for verified changes, preserving peer/B-ID traceability; do not mark comments posted merely because drafts exist.

For regression blocking, unresolved P0/P1 findings, failed required tests, missing required review, invented deadline/location/accessibility certainty, unselected-stop changes or leaked secrets are release blockers. Cosmetic observations should state their actual impact; do not weaken safety boundaries to make checks pass.

## Original-template restoration evidence

Route `858:10477`, Profile `858:10517`, empty plan `858:10447` and selected-stop cards `858:8605`/`858:8661` were inspected through high-fidelity design context. The implementation reuses original exported SVGs, navy/yellow/blue colours, Outfit, rounded surfaces and four-tab phone navigation. The Map and guide share the restored route card; selected stops retain edit, remove, reorder, completion and Undo. Each pending stop has its own timeline inside the original card treatment. Leave time includes preceding travel, queues and visits; the gate estimate and fixed arrival target stay distinct. Unknown inputs suppress precise times; late arrivals are labelled.

The user explicitly removed the persistent Demo journey note. Its banner test was replaced with checks that the banner is absent and accurate source information remains accessible in Help/About. This is a requirement change, not a relaxed check to hide a failure. Original icons retain their intrinsic geometry; invisible tap areas around compact controls meet the 44-point requirement.

The final local browser run passed 33 tests, including the active-route Undo regression, Map/Camera unavailable-state recovery, stop editing, timeline ordering/unknown values, preference-reset plan retention, original asset geometry and Profile touch targets. The 65 engine/backend/HTTP tests and four simulator-selection tests also passed. These results do not certify actual Camera guidance, connected accounts, trip history, translations or tutorial replay: their restored controls explain the current unavailable state. Figma designs and Haneda imagery were not edited.
